Mobile App + AI Integration (Compose UI, ViewModels, API wiring, Try-On UI)

Your Work (Explain in Viva)

  • Android app architecture: Navigation graph, screen routes, state management with ViewModels and repositories.
  • API integration: Retrofit ClosetAiApi, base URL switching via Settings, error handling, pagination.
  • Recommendations UI: grid, load more, like/dislike, saved items, and try-on entry points.
  • Try-on flow: image picker/selfie storage, request formation, base64 decode and render, local history (TryOnHistoryStore).
  • Wardrobe UI: add item dialog (category/color), upload to backend, store metadata to Firestore, realtime list updates.

Key Concepts

  • Why Compose: declarative UI, state-driven rendering, easy theming and navigation.
  • Repository pattern: decouple UI from networking + Firestore logic.
  • Handling latency: progress UI for try-on and retries; caching on device for smoother UX.

10 Viva Questions (with short answers)

1) What is the end-to-end flow from Home to Recommendations?Home collects context (occasion, lat/lon). ViewModel builds RecommendationRequest from Firestore profile + wardrobe. Retrofit calls backend. Results shown in grid with pagination.
2) Why did you use ViewModels + repositories?To keep UI logic thin, make testing easier, and centralize API/Firestore calls with consistent error handling and caching.
3) How do you handle base URL switching?Settings stores URL in ServerConfigStore; app reconfigures Retrofit via ApiClient.configureBaseUrl().
4) How is try-on requested from the app?Multipart upload: user selfie file + garment URL + parameters; backend returns base64 image which is decoded and displayed.
5) Where is wardrobe stored?Wardrobe metadata is stored in Firestore under users/{uid}/wardrobe. Images are uploaded to backend static storage and saved as URLs.
6) Why not store wardrobe images directly in Firestore?Firestore is document DB and not optimized for large binaries. We store only metadata + URL, which is scalable and cheaper.
7) How does the app show Saved items?Saved items are fetched via backend endpoint that returns liked item snapshots (server-side saved list).
8) How do you handle network failures?Show user-friendly error state, allow retries, and keep cached results (e.g., recommendations cache/history) to avoid blank screens.
9) What is the role of local stores like TryOnHistoryStore?Quick access to recent results even if backend is slow/unavailable; reduces repeated try-on requests.
10) What are the biggest UX challenges?Try-on latency, permissions (location/images), and ensuring onboarding doesn’t feel too long while collecting enough profile data.

10 Viva Questions (with short answers)

1) Why FastAPI over Flask?Better async support, built-in validation with Pydantic, auto OpenAPI docs, and cleaner typing.
2) How is wardrobe image upload implemented?Multipart UploadFile, validate content type, save under uploads directory, and return a public URL served by StaticFiles.
3) How do you avoid stale cached results?Use a cache version string; if payload/logic changes, increment version so keys change.
4) What is the structure of the recommendation endpoint?Accepts profile + context + pagination; scrapes candidates, caches, ranks, diversifies, then slices page.
5) Where is feedback stored?In Redis sets keyed by user id: liked/disliked ids; also saved snapshots for “saved items”.
6) How do you handle external failures (scraper/try-on)?Use timeouts, retries, clear HTTP error responses, and safe fallbacks (e.g., fallback cloth image for try-on).
7) Why do you return base64 for try-on output?It simplifies Android display without hosting generated files, and avoids extra storage or signed URLs.
8) How do you ensure the response always has an image URL?Sanitize the returned slice: if image_url blank, replace with a placeholder.
9) What is the connectivity endpoint used for?Quick check if e-commerce sites are reachable; helps diagnose 0-result scraping issues.
10) What’s the biggest backend bottleneck?Scraping and try-on inference latency; caching and concurrency reduce impact.

10 Viva Questions (with short answers)

1) Why is scraping needed?To fetch real-time product candidates when a public API isn’t available; keeps recommendations realistic.
2) What are the main risks of scraping?HTML layout changes, rate limiting, bot detection, and incomplete data. We mitigate via caching + connectivity checks.
3) How do you build a query for Myntra?From user preferences: category + style keywords + gender + budget constraints; generate a stable search term.
4) What fields do you extract?Title, brand, price, product URL, image URL, platform, plus optional match reasons/score later.
5) How do you handle missing images/prices?Fallback values, skip invalid entries, and backend sanitization for UI safety.
6) How do you validate scraper quality?Manual spot checks + counts, logging for 0 results, and testing with multiple queries.
7) How does caching help scraping?Scrape once, reuse candidates for pagination and feedback-aware ranking; reduces repeated requests to the site.
8) How can you make scraping more robust?Use multiple selectors, headless browser fallback, retry with alternate queries, and monitoring for changes.
9) What is the connectivity endpoint for?To confirm the target site is reachable; if blocked, scraper results will be zero.
10) Future improvement?Add multi-source scraping and a manager to merge/deduplicate candidates across sites.

  • Security: explain Firestore rules idea (only authenticated users access their docs).
  • Redis cache concept: why we need caching for scraper candidates and ranked results; feedback stored as sets.

Key Concepts

  • Why Firestore: serverless, real-time sync, simple integration with mobile.
  • Data separation: Firestore for persistent user data; Redis for fast temporary caches.

10 Viva Questions (with short answers)

1) Why use Firebase Auth?It provides secure Google sign-in without building an auth server; UID becomes a stable identifier.
2) What is the Firestore data model?users/{uid} profile doc + users/{uid}/wardrobe/{itemId} items with image URL and metadata.
3) Why not store everything in Redis?Redis is in-memory and not guaranteed durable; user profiles and wardrobes must persist reliably.
4) What is the difference between Firestore and Firebase Storage?Firestore stores documents; Storage stores large files. Here images are uploaded to backend and only URLs are stored.
5) How do Firestore security rules matter?They ensure only authenticated users can read/write their own profile/wardrobe data, preventing leaks.
6) Why Redis caching is helpful?Scraping is expensive; caching allows fast “Load more” and re-ranking without re-scraping.
7) What is a feedback set?A Redis structure storing liked/disliked product IDs per user to adjust ranking in later calls.
8) What happens if Redis is down?The backend can fall back to in-memory caching or re-scrape; functionality remains but performance drops.
9) How do you link Firestore user with backend requests?App includes UID in profile/request; backend uses it to fetch/store feedback and saved items in Redis.
10) What’s a privacy concern here?User images and preferences; must avoid public exposure, use authenticated access and minimal stored sensitive data.
RATIK
Recommendation Engine (MatchScorer, weather integration, feedback-aware ranking)
Click to toggle

Your Work (Explain in Viva)

  • MatchScorer: score each product using overlaps with user style/color/brand preferences and category relevance.
  • Weather-aware adjustments: if hot/rain/cold, boost relevant fabric/garment categories (rule-based).
  • Feedback-aware re-ranking: use liked/disliked sets to nudge future rankings.
  • Diversification: cap per platform and total results to keep UI usable.
  • Pagination: rank full candidate list, then slice by offset/limit for stable pages.

Key Concepts

  • Cold start: rule-based ranking works when no purchase history exists.
  • Explainability: match reasons can be returned so users understand why an item is recommended.

10 Viva Questions (with short answers)

1) What is MatchScorer?A rule-based ranking component that computes a match score per product using user preferences + context.
2) Why rule-based instead of ML model?Minor project + cold-start; rule-based is fast, explainable, and doesn’t need training data.
3) How is weather used?Backend fetches weather from OpenWeatherMap given lat/lon and adjusts scores (e.g., rain → boost rain-friendly items).
4) How does feedback affect ranking?Liked items increase preference weights; disliked IDs can be penalized or filtered to reduce repetition.
5) What is diversification and why needed?Prevents results from one source dominating; improves perceived variety and reduces duplicates.
6) What if the scorer returns empty results?Fallback to raw scraped candidates so the UI never shows empty state (demo reliability).
7) How do you make results stable across pages?Rank the full list first, then slice; caching keyed by feedback version keeps consistency.
8) What are “match reasons”?Human-readable explanations (e.g., “matches your casual style”, “good for warm weather”) generated alongside scores.
9) What are typical scoring features?Style keywords, color preferences, brand affinity, category relevance, budget/price fit, and context (occasion/weather).
10) Future improvement?Replace rules with embeddings + learning-to-rank, and use outfit compatibility modeling for wardrobe matching.
